## Step 12: browser export

The saved fixture was opened from `fixture space #hash/export-check.md`. It contains a relative PNG, table, nested list, fenced Python block inside a list item, and duplicate `Same` headings linked as `#same` and `#same-2`.

The actual palette command created `/tmp/MarkdownGlance/export-check-f6ee52f3.html`; browser inventory confirmed Chrome opened that file with title `export-check.md`. A new, unsaved Markdown buffer containing the same source created `Untitled-4d134bc0.html`. Both files have mode `0600`. The command was absent from the palette in a Plain Text buffer.

Static inspection of the generated saved HTML confirms:

- The image URL encodes the parent directory as `fixture%20space%20%23hash`.
- Both fragment links and matching heading IDs exist, with no `<base>` element.
- The table, nested `<ul>` and `<pre><code class="language-python">` inside a list item survive export.
- Unsaved output retains the same structure. Its relative image remains `pixel.png`, because an unsaved buffer has no source directory; image resolution for that case is not claimed.

The native preview displayed the corresponding list nesting and fenced block. The adjacent unordered and ordered source lists were parsed as one unordered list in both outputs; this is not evidence of an export/preview mismatch. An earlier chat inference that export preserved ordered numbering was corrected after reading the generated HTML.

**Original file transport remains unverified:** the browser tool rejected the `file://` URL under its URL security policy. That page was not inspected through alternative browser automation. The original image was a one-pixel fixture; it was replaced with a visible 160 × 64 green/yellow checkerboard and the saved export command was run again. Earlier preview screenshots show the original one-pixel image. The following HTTP test covers browser rendering separately.

### HTTP follow-up

At the user's request, `tests/browser_export.py` now provides an unattended
HTTP browser check. It generates a fresh synthetic page through the real
`standalone_html` renderer with an empty source base path. It serves only an
in-memory harness, that page, and a generated checkerboard PNG. It does not
serve the blocked exported file or map arbitrary local file URLs onto HTTP.

Two real browser runs passed all ten assertions: one opened through the
browser tool ([result](manual-2026-09-06/http-browser12.json)), and one started
entirely by the command's `--open-browser` option
([result](manual-2026-09-06/http-browser12-unattended.json)). The latter required
no further interaction, wrote its JSON, closed the server, and exited 0.

Assertions cover image decode and dimensions, the encoded space/hash directory,
absence of `<base>`, table rows, nested-list structure and measured indentation,
the fenced block inside a list item, distinct heading IDs, and actual anchor
clicks selecting the correct `:target` while retaining the same page URL.
Browser screenshots also showed the table, nested list and code-block shape
seen in the native preview. These are HTTP results, not proof of the original
file transport or exact pixel equivalence to minihtml.

The browser runs used Chrome 152 and system Python 3.10.12 with the same
Package Control libraries through `PYTHONPATH`; they were separate from the
Sublime Python 3.8 checks above. Reproduction command on this test environment:

```bash
cd /home/fruit/dev
PYTHONPATH=/tmp/mdglance-manual-a576p_jy/sublime/Data/Lib/python38 \
  python3 -m MarkdownGlance.tests.browser_export --open-browser \
  --output MarkdownGlance/docs/verification/http-browser.json
```

The helper also passed a failure-path check: unlisted and traversal-shaped
URLs return 404; no browser result produces timeout JSON, exit status 1, and a
closed listener. Python compilation passed. No server remains running after
these checks.

## Step 14: manual install without libraries

The checkout was cloned into a separate portable profile's `Data/Packages/MarkdownGlance` before startup. The missing-library dialog named `Markdown` and `pymdown-extensions` and instructed the user to run `Package Control: Satisfy Libraries`, then restart Sublime Text.

With Package Control initially present, its startup maintenance automatically installed the missing libraries. To keep the missing state stable for the repeat-command check, Package Control and the libraries were moved into test-only backup directories and Sublime was restarted. The preview command remained in the palette and invoking it repeated the same dialog.

Package Control was restored. After its automatic installation was observed, the two library directories and their metadata were moved aside again while the instance remained running. This made the palette's `Satisfy Libraries` invocation actually reinstall both libraries; the console reported both installations and `All libraries have been satisfied!`. After a full Sublime restart, the preview rendered normally.

A final clean missing-library replay captured the complete startup console: the package loaded, then emitted the expected missing-library message, with no traceback. The recovery-session screenshot also contains a preceding `SyntaxError` caused by an automation attempt typing a palette label into the Python console. That error was from the test interaction, not plugin import or execution; the separate clean replay log establishes the no-traceback result.

## Step 15: MarkdownPreview and Pygments

`MarkdownPreview` 2.8.2 was installed through the real Package Control palette beside the manual MarkdownGlance installation. Its metadata declares Python 3.3, so Package Control installed Pygments 2.1 into `Lib/python33`. After restart, the actual MarkdownGlance preview rendered the Mermaid diagram and Python fence normally. Its Python 3.8 console reported that Pygments was unavailable in that runtime.

For the intended shared-runtime regression check, a test-only package named `ManualPygmentsFixture` declared `.python-version` as `3.8` and `Pygments` in `dependencies.json`. It contained no plugin code. Package Control's `Satisfy Libraries` installed Pygments 2.19.2 into `Lib/python38`.

After another full restart:

- The live console imported Pygments 2.19.2 from `Data/Lib/python38/pygments/__init__.py`.
- MarkdownGlance's actual parser output retained `class="language-mermaid"` and `class="language-python"`.
- The native preview visibly rendered the Mermaid diagram and Python block.
- The [complete coexistence console](manual-2026-09-06/coexist-console15.log) contained no traceback.

Only synthetic diagram text was used with `enable_mermaid` enabled.

## Plan observations

Step 14 should explicitly account for Package Control's startup library installation when setting up a persistent missing-library case. Without Package Control installed, the proposed repair command also requires installing Package Control first.

Step 15 should verify `pygments.__file__` in MarkdownGlance's Python 3.8 runtime. Installing another package is insufficient when it uses a different plugin host. The supplemental fixture above closes that coverage gap.

No product code or dependencies were changed. The HTTP follow-up added a developer test helper and documented its automation command without redefining file-transport acceptance. Linux/ST 4200 is covered here; macOS, Windows and newer dev builds were not tested.
